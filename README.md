---

`islamic_kit_android` is the native Kotlin port of the Dart package
[`islamic_kit_plus`](https://github.com/bilalelsayed97/islamic_kit_plus)
**0.3.0**. It computes **everything on-device**. There are **no network
requests** to aladhan.com or any other service, and the port is **behaviourally
identical** to the Dart engine: the same numbers, the same strings, the same
JSON, the same fallbacks — proven by the ported Dart test suite and a
cross-language conformance suite generated by the Dart implementation (see
[Testing](#testing)). Every deliberate difference is listed under
[Parity notes](#parity-notes).

Prayer times are solved from **Jean Meeus' solar position** (*Astronomical
Algorithms*, 2nd ed.), with the sun's right ascension and declination
interpolated across three days so every event is computed at the moment it
occurs rather than at a fixed seed hour. Around it sit the Moonsighting
Committee twilight, a Hijri calendar with four methods, and the qibla
calculation. JSON output mirrors the
[aladhan.com Prayer Times API](https://aladhan.com/prayer-times-api)
response **shape**.

The calculation core (prayer times, Hijri calendar, qibla, calendars) is a
**plain Kotlin/JVM library** — no Android SDK, no SQLite; its only dependencies
are the Kotlin standard library and `androidx.annotation`. The optional
by‑city / by‑address geocoder is an Android library that reads a bundled SQLite
database of **265,849 places** across 251 countries and 371 timezones —
131,090 of them populated settlements, which is what city search and reverse
geocoding match against.

## Highlights

- 🕌 **Prayer times** from the Meeus solar algorithm, with 34 calculation
  methods, Asr schools, high‑latitude rules, midnight modes, per‑prayer tuning,
  and elevation.
- 🌙 **Moonsighting Committee Worldwide** Fajr/Isha (general / red / white shafaq).
- 📅 **Hijri ↔ Gregorian** conversion with four calendar methods, month lengths,
  and Islamic holidays.
- 🗓️ **Calendars** — monthly, annual, and date‑range, in both Gregorian and Hijri.
- 🧭 **Qibla** direction (great‑circle bearing to the Ka'aba).
- 🏙️ **Offline geocoding** — bundled database of 265,849 places (131k
  settlements) with English + Arabic names, behind a swappable `Geocoder`
  interface.
- 🌐 **EN/AR localization** for prayer, month, and weekday names, plus a
  `title` / `description` on every enum for building settings UIs.
- 🔌 **aladhan‑shaped** `toAladhanJson()` — the same response structure and key
  order, so an existing aladhan client parses it unchanged.
- 🧱 **Clean architecture**, immutable `data class` value objects, a core that
  runs on any JVM, `@JvmOverloads` / `@JvmStatic` throughout for Java callers.
- 🔁 **Parity with the Dart package** — every Dart test ported, plus 55k+
  conformance cases generated by the Dart implementation.

## Install

The library is distributed through [JitPack](https://jitpack.io/#bilalelsayed97/islamic_kit_android).

```kotlin
// settings.gradle.kts
dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
        maven("https://jitpack.io")
    }
}
```

```kotlin
// build.gradle.kts (module)
dependencies {
    // Prayer times, Hijri calendar, qibla, calendars, aladhan JSON, EN/AR labels:
    implementation("com.github.bilalelsayed97.islamic_kit_android:core:0.3.1")

    // Only where you need the bundled city database (brings :core with it):
    implementation("com.github.bilalelsayed97.islamic_kit_android:geocoding:0.3.1")
}
```

Requirements:

- **Kotlin ≥ 2.3.** The artifacts are compiled with Kotlin 2.4.0, and a Kotlin
  compiler reads metadata at most one minor version ahead of itself. Both
  artifacts depend on `kotlin-stdlib` 2.4.0.
- **`:core`** is a JVM jar with Java 17 bytecode. It has no Android dependency
  and works in a plain JVM project, a unit test, or an Android module.
- **`:geocoding`** is an AAR with `minSdk 24`, built against `compileSdk 36`;
  its AAR metadata requires the consuming module to compile against
  **`compileSdk` 36 or newer**.
- The core API is usable on `minSdk 24` without core‑library desugaring: dates
  and offsets are the library's own `CivilDate` / `CivilDateTime` / `UtcOffset`.
  The optional `java.time` bridges are annotated `@RequiresApi(26)`.

### The 37 MB database asset

`:geocoding` ships `prayer_times.db` (37,093,376 bytes) as an **asset**. Two
things follow:

- **APK size.** AAPT deflates assets by default, so the database costs about
  16 MB in your APK. The library reads it as a stream (`AssetManager.open`),
  which works whether or not the asset is compressed, so no packaging option is
  required. If you would rather trade APK size for a faster first launch, store
  it uncompressed:

  ```kotlin
  android {
      androidResources { noCompress += "db" } // optional
  }
  ```

- **On‑device size.** SQLite opens files by path, so on first use the asset is
  copied once to `noBackupFilesDir/islamic_kit/islamic_kit_prayer_times_v2.db`
  (37 MB, excluded from Auto Backup) and opened read‑only from there on every
  later launch. See [Geocoding](#geocoding).

If you only need prayer times for coordinates you already have, depend on
`:core` alone and none of this applies.

## Quick start

```kotlin
import io.github.bilalelsayed97.islamickit.application.PrayerTimesService
import io.github.bilalelsayed97.islamickit.domain.enums.CalculationMethod
import io.github.bilalelsayed97.islamickit.domain.enums.Language
import io.github.bilalelsayed97.islamickit.domain.enums.Prayer
import io.github.bilalelsayed97.islamickit.domain.enums.TimeFormat
import io.github.bilalelsayed97.islamickit.domain.valueobjects.CalculationParameters
import io.github.bilalelsayed97.islamickit.domain.valueobjects.Coordinates
import io.github.bilalelsayed97.islamickit.time.CivilDate
import io.github.bilalelsayed97.islamickit.time.UtcOffset

val service = PrayerTimesService()

val result = service.timings(
    CivilDate(2014, 4, 24),
    Coordinates(51.508515, -0.1254872), // London
    CalculationParameters(
        method = CalculationMethod.ISNA,
        utcOffset = UtcOffset.ofHours(1), // London BST
    ),
)

println(result.formatted(Prayer.FAJR))                // 03:57
println(result.formatted(Prayer.ASR, TimeFormat.H12)) // 4:56 pm
println(Prayer.MAGHRIB.title(Language.AR))            // المغرب
println(result.date.hijri.day)                        // 24  (24-06-1435)
```

`timings` can throw `IllegalArgumentException` (see [Errors](#errors)): the
date block runs the Hijri converter, which rejects dates outside its table.

## Dates & offsets

The engine is timezone‑free, so the API does not take `java.util.Date` or
`java.time` types. It takes three small value types of its own, all usable on
`minSdk 24`:

```kotlin
// A calendar date with no time of day and no zone. The constructor is strict.
val date = CivilDate(2014, 4, 24)
date.plusDays(1)        // 2014-04-25
date.isoDayOfWeek       // 4 (Monday = 1 … Sunday = 7)
CivilDate.normalized(2014, 2, 30) // 2014-03-02 — Dart's DateTime(y, m, d) overflow rule
// CivilDate(2014, 2, 30) throws IllegalArgumentException

// "Today" and "now" on the wall clock of a zone (default: the device zone).
val cairo = TimeZone.getTimeZone("Africa/Cairo")
val today: CivilDate = CivilDate.today(cairo)
val now: CivilDateTime = CivilDateTime.now(cairo)
CivilDateTime(2014, 4, 24, 13, 30) // 2014-04-24T13:30:00

// A fixed offset from UTC, stored as whole seconds.
UtcOffset.ofHours(1)          // +01:00
UtcOffset.ofHours(5, 30)      // +05:30
UtcOffset.ofHours(-3, -30)    // -03:30 (both parts carry the sign)
UtcOffset.ofMinutes(345)      // +05:45
UtcOffset.parse("+05:30")     // also "+0530", "+05", "Z"
UtcOffset.ZERO

// The DST-correct offset of an IANA zone for a date (the offset at local noon):
val london = TimeZone.getTimeZone("Europe/London")
UtcOffset.of(london, CivilDate(2014, 4, 24)) // +01:00 (BST)
UtcOffset.of(london, CivilDate(2014, 1, 15)) // +00:00 (GMT)
UtcOffset.of(london, 1398337200000L)         // the offset at an instant (epoch millis)
```

### `java.time` interop (API 26+)

Optional bridges in `io.github.bilalelsayed97.islamickit.time`, every one
annotated `@RequiresApi(26)` — available on any JVM, and on Android from API 26
or with core‑library desugaring:

```kotlin
import io.github.bilalelsayed97.islamickit.time.toCivilDate
import io.github.bilalelsayed97.islamickit.time.toInstant
import io.github.bilalelsayed97.islamickit.time.toLocalDate
import io.github.bilalelsayed97.islamickit.time.toZonedDateTime
import io.github.bilalelsayed97.islamickit.time.toZoneOffset
import io.github.bilalelsayed97.islamickit.time.utcOffsetAt

val zone = ZoneId.of("Europe/London")
val date: CivilDate = LocalDate.of(2014, 4, 24).toCivilDate()
val offset: UtcOffset = zone.utcOffsetAt(date)   // +01:00, the offset at local noon
offset.toZoneOffset()                            // ZoneOffset +01:00
date.toLocalDate()                               // LocalDate 2014-04-24

val fajr = service.timings(date, coords, params.copy(utcOffset = offset)).time(Prayer.FAJR)
fajr.toInstant()             // 2014-04-24T02:57:00Z   (null when the time is invalid)
fajr.toZonedDateTime(zone)   // 2014-04-24T03:57+01:00[Europe/London]
```

Also available: `CivilDateTime.toLocalDateTime()`, `LocalDateTime.toCivilDateTime()`
(nanoseconds are dropped) and `ZoneOffset.toUtcOffset()`.

## Zero-config & automatic per-location settings

You don't have to set every enum. There are four levels of "automatic":

**1. Sensible global defaults.** Every field of `CalculationParameters` has a
default (`method = MWL`, `school = STANDARD`, `highLatitudeRule = MIDDLE_OF_NIGHT`,
`calendarMethod = HJCOSA`, `shafaq = GENERAL`, `imsakMinutes = 10`, …), so you
only supply the UTC offset:

```kotlin
service.timings(
    CivilDate(2024, 4, 24),
    Coordinates(21.42, 39.83),
    CalculationParameters(utcOffset = UtcOffset.ofHours(3)), // that's it
)
```

(`params` itself is optional too — `service.timings(date, coords)` computes MWL
times at UTC.)

**2. Fully automatic by city.** `timingsByCityAuto` needs **no presets at all** —
it picks the calculation method and Asr school from the city's country (the
offline equivalent of aladhan choosing "the closest authority based on location")
and takes the UTC offset from the city record:

```kotlin
// No method, school, or offset needed — all inferred from "Cairo, EG":
val result = service.timingsByCityAuto("Cairo", date = CivilDate.today(), country = "EG")
// -> Egyptian method, UTC+02:00
```

With a plain `PrayerTimesService()` this resolves against the curated 103‑city
set; pass the SQLite geocoder (below) to resolve against all 131k settlements.

**3. Recommended params you can reuse (e.g. with coordinates).** Get the
recommended method + school for a country and pass it anywhere (timings,
calendars, next prayer), overriding anything you like with `copy()`:

```kotlin
val params = service.recommendedParams("PK", utcOffset = UtcOffset.ofHours(5))
// -> KARACHI method + HANAFI school
service.monthlyCalendar(2024, 4, coords, params)

// Or resolve straight from a country code:
val m: CalculationMethod = LocationDefaults.methodForCountry("US") // ISNA
val s: AsrSchool = LocationDefaults.schoolForCountry("TR")         // HANAFI
```

**4. Fully automatic from a GPS fix.** With the city database open,
`autoParamsForCoordinates` takes a latitude and longitude, finds the nearest
city, and reads the calculation method from that city's country as recorded in
the database (all 251 of them) plus the UTC offset and IANA name of its
timezone:

```kotlin
// :geocoding — blocking file I/O, so call this off the main thread (see Geocoding).
val handle: BundledCityDatabase.Handle = BundledCityDatabase.open(context)
val service = PrayerTimesService(geocoder = handle.geocoder, directory = handle.directory)

// Everything inferred from the coordinates (null if no city resolves):
val result = service.timingsByCoordinatesAuto(21.4225, 39.8262, date = CivilDate.today())
// -> Umm al-Qura (MAKKAH), UTC+3, meta.timezone = "Asia/Riyadh"

// Or just the parameters, to reuse elsewhere:
val params: CalculationParameters? = service.autoParamsForCoordinates(21.4225, 39.8262)
```

The `Handle` owns the one read‑only SQLite connection that its `geocoder` and
`directory` share. Keep it for the **process lifetime** (an `Application`‑scoped
singleton) and `close()` it only if you really are done — closing it closes
both. Without a `directory`, `autoParamsForCoordinates` and
`timingsByCoordinatesAuto` throw `IllegalStateException`.

**Country → method** defaults (`LocationDefaults`, the fallback when the
database is not open): US/MX → ISNA, CA → Canada, SA/YE/BH/SY/VN → Makkah,
AE → Dubai, KW → Kuwait, QA → Qatar, OM → Oman, EG/NG → Egypt, SD/SS → Sudan,
IQ → Iraq, LY → Libya, JO → Jordan, DZ → Algeria, MA/EH → Morocco,
TN → Tunisia, IR → Tehran, TR → Turkey, RU → Russia, TJ → Tajikistan,
PK/IN/BD/AF → Karachi, MV → Maldives, ID/MY/SG → Singapore, BN → JAKIM,
FR/MF → France, PT → Portugal, DE → Munich, AT → Vienna, BE → Belgium,
LU → Luxembourg — everything else → Muslim World League. Hanafi Asr is the
default for PK, IN, BD, AF, TR. All of this is overridable.

> The one thing not auto-detected from the database is **daylight saving** —
> bundled city offsets are standard time. `java.util.TimeZone` can fill the
> gap; see [Timezones & DST](#timezones--dst).

## Core concepts

| Type | What it is |
|---|---|
| `PrayerTimesService` | The **facade** you call for every feature. Immutable — construct once and reuse from any thread. |
| `Coordinates(latitude, longitude)` | A geographic point in decimal degrees. |
| `CalculationParameters` | Immutable `data class` holding all calculation settings. Use `copy()` to tweak. |
| `CivilDate(year, month, day)` | A calendar date with **no time zone** — the port of the date‑only `DateTime` the Dart package passes around. Strict constructor; `normalized(y, m, d)` reproduces Dart's overflow (`2014‑02‑30` → `2014‑03‑02`); `today(timeZone)`, `plusDays`, `plusMonths`, `isoDayOfWeek` (Mon = 1), `epochDay`, `Comparable`. |
| `CivilDateTime` | A `CivilDate` plus wall‑clock `hour`/`minute`/`second`; `now(timeZone)`. Used by `nextPrayer`. |
| `UtcOffset` | A fixed offset in seconds: `ofHours(5, 30)`, `ofMinutes`, `ZERO`, `parse("+05:30")`, `of(TimeZone, date)`. The port of the Dart `Duration utcOffset`. |
| `PrayerResult` | The result of a timings call: `timings` + `date` (Gregorian + Hijri) + `meta`. |
| `PrayerTimings` | The set of computed times; `time(prayer)`, `formatted(prayer, format)`, `toFormattedMap()`, and `raw`. |
| `PrayerTime` | A single time; `format()`, `toEpochMillis()`, `isValid`, `name(language)`, `hours`. |
| `NextPrayer` | The next upcoming prayer, its `time`, and the `onDate` it falls on. |
| `QiblaDirection` | Bearing to the Ka'aba (`degrees` clockwise from true north). |

### Errors

Where the Dart package throws `ArgumentError` / `StateError`, the Kotlin port
throws the **unchecked** `IllegalArgumentException` / `IllegalStateException`
with the same message text. Nothing in the API is a checked exception except
the `IOException` of `BundledCityDatabase`.

| Exception | When |
|---|---|
| `IllegalArgumentException` | A Gregorian date outside a Hijri table's range (HJCoSA / UAQ: 1937‑03‑14 … 2077‑11‑16; Diyanet: 1900‑05‑01 … 2028‑01‑26). Every timings/calendar call can throw this because the date block runs the converter. |
| `IllegalArgumentException` | A Hijri date outside the table (UAQ 1356–1500 AH, Diyanet 1318–1449 AH). |
| `IllegalArgumentException` | `rangeCalendar` with `end` before `start` or a span over 11 months; an invalid `CivilDate` / `CivilDateTime` / `UtcOffset.parse` input; `Prayer.fromKey` with an unknown key; `JsonWriter.encode` with NaN/∞ or an unsupported type. |
| `IllegalStateException` | The geocoder returned nothing for a `*ByCity` / `*ByAddress` query (`Location not found: "…"`). |
| `IllegalStateException` | `autoParamsForCoordinates` / `timingsByCoordinatesAuto` without a `directory`. |
| `IOException` | `BundledCityDatabase.materialize` / `open*` when the asset cannot be copied. |

```kotlin
try {
    service.timings(CivilDate(2100, 3, 1), coords, params)
} catch (e: IllegalArgumentException) {
    println(e.message) // Gregorian date out of range for HJCoSA ((1937, 3, 14) .. (2077, 11, 16)).
}
```

## Configuration — `CalculationParameters`

Every setting is optional and immutable. Defaults are shown.

| Field | Type | Default | Description |
|---|---|---|---|
| `method` | `CalculationMethod` | `MWL` | The twilight authority (see below). |
| `customMethod` | `MethodParams?` | `null` | Angles/intervals used when `method` is `CUSTOM`. |
| `school` | `AsrSchool` | `STANDARD` | Asr shadow factor (Standard = 1, Hanafi = 2). |
| `asrShadowFactor` | `Double?` | `null` | Overrides the school's shadow factor when set. |
| `midnightMode` | `MidnightMode?` | `null` | Overrides the midnight basis. Unset resolves to `JAFARI` (sunset → Fajr), the engine's basis. |
| `highLatitudeRule` | `HighLatitudeRule` | `MIDDLE_OF_NIGHT` | High‑latitude Fajr/Isha bound. `NONE` disables it. |
| `utcOffset` | `UtcOffset` | `UtcOffset.ZERO` | **You provide this.** Offset for the target date (include DST). |
| `elevation` | `Double` | `0.0` | Observer elevation in metres. Dips the horizon, so sunrise comes earlier and sunset later. A package extension — the reference engine assumes sea level. |
| `shafaq` | `Shafaq` | `GENERAL` | Twilight used by the Moonsighting method for Isha. |
| `tune` | `Tune` | `Tune.NONE` | Per‑prayer offsets in minutes (aladhan `tune`). |
| `imsakMinutes` | `Int` | `10` | Minutes before Fajr for Imsak. |
| `dhuhrMinutes` | `Int` | `0` | Minutes added to Dhuhr. |
| `calendarMethod` | `CalendarMethod` | `HJCOSA` | Hijri method for the date block. |
| `timezoneName` | `String?` | `null` | Optional label echoed in `meta.timezone` (otherwise `UTC+01:00`‑style). |

```kotlin
val base = CalculationParameters(method = CalculationMethod.EGYPT)
val tuned = base.copy(
    school = AsrSchool.HANAFI,
    utcOffset = UtcOffset.ofHours(2),
    tune = Tune(fajr = -2, isha = 3), // minutes; see "Per-prayer tuning"
)
```

`copy()` is the Kotlin spelling of Dart's `copyWith`, and a superset of it:
because it is a real named‑argument call, it can also **clear** a nullable
field, which `copyWith` cannot —

```kotlin
val labelled = tuned.copy(timezoneName = "Africa/Cairo")
val cleared = labelled.copy(timezoneName = null, midnightMode = null)
```

The resolved values are exposed as `effectiveParams`, `resolvedMidnightMode`,
`resolvedShadowFactor` and `resolvedHighLatitudeRule`.

### Per-prayer tuning (the aladhan `tune` parameter)

Shift any prayer by a number of minutes with `Tune`. Its field order matches the
aladhan contract exactly — `Imsak, Fajr, Sunrise, Dhuhr, Asr, Maghrib,
Sunset, Isha, Midnight` (Maghrib precedes Sunset) — so you can build it from, or
export it to, the aladhan `tune` CSV:

```kotlin
// Named fields
val tune = Tune(fajr = 3, dhuhr = 7, isha = 8)

// From/to the aladhan "tune" query string
val parsed = Tune.fromCsv("5,3,5,7,9,-1,0,8,-6")
parsed.toCsv() // "5,3,5,7,9,-1,0,8,-6"

val params = CalculationParameters(
    method = CalculationMethod.MWL,
    utcOffset = UtcOffset.ofHours(3),
    tune = tune,
)
```

The applied offsets are echoed in the aladhan `meta.offset` block, just like the API.

## Enums (with EN/AR labels)

Every input is a typed enum, and **every enum implements `Localized`**, which
exposes UI metadata in both languages:

```kotlin
val label = CalculationMethod.MWL.title(Language.AR)    // رابطة العالم الإسلامي
val help = AsrSchool.HANAFI.description(Language.EN)
// "Asr begins when an object's shadow is twice its own length (shadow factor 2)."

// One settings-list adapter for every enum:
val options: List<Localized> = CalculationMethod.entries
val labels = options.map { it.title(Language.EN) }
```

| Enum | Entries |
|---|---|
| `Prayer` | `IMSAK`, `FAJR`, `SUNRISE`, `DHUHR`, `ASR`, `SUNSET`, `MAGHRIB`, `ISHA`, `MIDNIGHT`, `FIRST_THIRD`, `LAST_THIRD` |

### Ramadan

`MAKKAH` is the only method whose Isha interval changes with the season: Umm
al‑Qura lengthens 90 minutes to 120 for Ramadan. The switch is resolved from
the **date being computed** (against the Umm al‑Qura table, whatever
`calendarMethod` you chose), so a calendar generated months ahead still gets
it right. Dates the table cannot express are simply "not Ramadan".

## Reading & formatting times

`PrayerResult` gives you three views of each time:

```kotlin
val result = service.timings(date, coords, params)

// 1) Formatted string
result.formatted(Prayer.FAJR)                        // "03:57"  (24h default)
result.formatted(Prayer.FAJR, TimeFormat.H12)        // "3:57 am"
result.formatted(Prayer.FAJR, TimeFormat.ISO8601)    // "2014-04-24T03:57:00+01:00"

// 2) The PrayerTime object
val t = result.time(Prayer.MAGHRIB)
t.isValid          // false only at extreme latitudes
t.format()         // "20:12"
t.toEpochMillis()  // 1398366720000 — the absolute instant (Long?, null when invalid)

// 3) A whole map, or the raw hours
result.timings.toFormattedMap()   // Map<Prayer, String>  {FAJR=03:57, ...} in Prayer order
result.timings.raw[Prayer.FAJR]   // 3.95 — fractional hours (Double?, null if invalid)
for ((prayer, hours) in result.timings.raw) { /* Prayer order */ }
```

`toEpochMillis()` is the port of Dart's `toUtc()`: hand it to
`Date(millis)`, `Instant.ofEpochMilli`, `AlarmManager`, or WorkManager delays.
On API 26+ `toInstant()` / `toZonedDateTime(zone)` do it for you.

`TimeFormat` options: `H24` (`03:57`), `H12` (`3:57 am`), `H12_NO_SUFFIX`
(`3:57`), `FLOAT` (raw hours, e.g. `3.95`), `ISO8601`. Times that cannot be
computed return the sentinel `TimeFormatting.INVALID_TIME` (`-----`).

Raw hours are relative to the *local* civil day and may run below 0 or past
24 when an event rolls into the neighbouring day (Last Third is often
`> 24`); the clock formats wrap, and `ISO8601` moves the date instead —
`2014-04-25T01:22:00+01:00` for that day's Last Third.

## Hijri calendar conversion

```kotlin
val factory = HijriConverterFactory()

val hijri = factory.create(CalendarMethod.HJCOSA).fromGregorian(CivilDate(2025, 2, 14))
hijri.day         // 15
hijri.month       // 8
hijri.monthEn     // "Sha'ban"
hijri.monthAr     // "شَعْبان"
hijri.monthLength // 29
hijri.formatted   // "15-08-1446"
hijri.holidays    // ["Lailat-ul-Bara'at", …] — observances on this day (may be empty)

val gregorian = factory.create(CalendarMethod.UAQ).toGregorian(1446, 8, 15) // 2025-02-14
```

| Method | Basis | Valid range |
|---|---|---|
| `HJCOSA` (default) | Umm al‑Qura table + Saudi sighting overrides | 1356–1500 AH |
| `UAQ` | Umm al‑Qura table | 1356–1500 AH |
| `DIYANET` | Diyanet table | 1318–1449 AH |
| `MATHEMATICAL` | Pure arithmetic; supports a day `adjustment` | unrestricted |

```kotlin
// Mathematical supports a +/- day adjustment in both directions
factory.create(CalendarMethod.MATHEMATICAL)
    .fromGregorian(CivilDate(2025, 2, 14), adjustment = 1) // day 16
factory.create(CalendarMethod.MATHEMATICAL)
    .toGregorian(1446, 8, 15, adjustment = -1)             // 2025-02-13
```

Out‑of‑range dates on table methods throw `IllegalArgumentException`. The same
date gives 1446‑08‑15 under HJCoSA and UAQ (a 29‑day month) and under the
mathematical calendar, but 1446‑08‑16 (30 days) under Diyanet — the tables
genuinely differ. The mathematical calendar does not track true month
lengths: its `monthLength` is **always 30**, exactly as in the Dart package.

## Geocoding

By‑city / by‑address lookups go through the `Geocoder` **interface**, so you can
choose your source or plug in your own.

### Option A — bundled SQLite database (recommended)

`:geocoding` ships a 265,849‑place database — 131,090 populated settlements
plus their administrative divisions — with English + Arabic names, coordinates
and standard‑time offsets.

Android's SQLite opens files by path, and an asset inside an APK has no path.
So `BundledCityDatabase` **materializes** the asset once — streamed to a `.tmp`
sibling, `fsync`ed and renamed into place, so an interrupted copy never leaves
a truncated file that would pass the reuse check — into
`context.noBackupFilesDir/islamic_kit/islamic_kit_prayer_times_v2.db`, then
opens it **read‑only** (`OPEN_READONLY | NO_LOCALIZED_COLLATORS`). Later
launches find the non‑empty file and skip the copy. The version marker in the
file name means a future database update lands under a new path instead of
silently reusing the old copy. `noBackupFilesDir` keeps the 37 MB out of Auto
Backup.

All of this is blocking file I/O, annotated `@WorkerThread`. Open it once, off
the main thread, and keep the result for the process lifetime:

```kotlin
/** Application-scoped holder: one connection, one service, for the whole process. */
class PrayerKit(context: Context) : AutoCloseable {
    private val handle: BundledCityDatabase.Handle =
        BundledCityDatabase.open(context.applicationContext)

    val directory: SqliteCityDirectory get() = handle.directory

    val service = PrayerTimesService(geocoder = handle.geocoder, directory = handle.directory)

    override fun close() = handle.close()
}

// e.g. from Application.onCreate — never on the main thread:
val io = Executors.newSingleThreadExecutor()
val kit: Future<PrayerKit> = io.submit<PrayerKit> { PrayerKit(context) }

// later, on a worker:
kit.get().service.timingsByCity("London", date = CivilDate.today(), country = "GB")
```

With coroutines the same call goes inside `withContext(Dispatchers.IO) { … }`;
the library itself has no coroutine dependency.

`BundledCityDatabase` also offers the pieces individually:

```kotlin
val geocoder: SqliteCityGeocoder = BundledCityDatabase.openGeocoder(context)
val directory: SqliteCityDirectory = BundledCityDatabase.openDirectory(context)

// Or manage the file yourself (a second argument picks another directory):
val file: File = BundledCityDatabase.materialize(context)
val custom = SqliteCityGeocoder(BundledCityDatabase.openDatabase(file))
```

`openGeocoder` and `openDirectory` each open their **own** connection; use
`open(context)` when you want both, so they share one. `SqliteCityGeocoder`,
`SqliteCityDirectory` and `Handle` are `Closeable`.

The `state` argument of `search` / `resolve` is ignored by this geocoder and
`City.state` is always `null` — the bundled database has no administrative‑region
column. `City.utcOffset` is the standard‑time offset and does not account for
DST; zones that are not a whole hour are handled (Tehran resolves to `+03:30`,
Delhi to `+05:30`).

### Option B — curated, zero‑dependency fallback

The default geocoder (`BundledCityGeocoder`, in `:core`) is a small curated set
of 103 cities that needs no database and works on any JVM:

```kotlin
val service = PrayerTimesService() // uses BundledCityGeocoder
service.timingsByCity("London", date = CivilDate.today(), country = "GB")
```

### Option C — your own geocoder

```kotlin
class MyGeocoder : Geocoder {
    override fun search(query: String, country: String?, state: String?): List<City> = listOf(
        City("Null Island", "XX", Coordinates(0.0, 0.0), UtcOffset.ZERO),
    )
}

val service = PrayerTimesService(geocoder = MyGeocoder())
```

`resolve(query, country, state)` (first match) comes free as a default method of
the interface. `country` accepts an ISO‑3166 alpha‑2 code (`"GB"`) or a common
name (`"United Kingdom"`).

## City directory (pickers & reverse geocoding)

`Geocoder` answers *"which city is this text?"*. `CityDirectory` — an interface
in `:core`, implemented by `SqliteCityDirectory` in `:geocoding` — answers the
questions a location‑picker asks instead, reading English and Arabic names
together so either locale renders without a second lookup:

```kotlin
val directory: SqliteCityDirectory = handle.directory

directory.countries(query = "مصر")          // -> [CountryInfo(Egypt, EG)]  (id 65)
directory.citiesInCountry(65, limit = 50)    // most prominent first, paged (limit / offset)
directory.searchCities(query = "Cairo")      // matches either language
directory.nearestCity(30.06263, 31.24967)    // -> CityEntry(Cairo, EG), timeZoneId "Africa/Cairo"
directory.timeZonesForCountry(65)            // -> [TimeZoneInfo(Africa/Cairo)] + Arabic label
directory.country(65)                        // -> CountryInfo(Egypt, EG)
```

Two behaviours are worth knowing, because the naive query gets both wrong:

- **`nearestCity` is not a plain proximity sort.** The database records
  neighbourhoods alongside the cities containing them, so the closest row to
  central Cairo is a neighbourhood, not Cairo. Distance is weighted by
  settlement prominence, letting a nearby capital or administrative seat
  outrank a marginally closer suburb.
- **`timeZonesForCountry` filters border noise.** A handful of Egyptian border
  towns carry `Asia/Jerusalem`, which would present Egypt as a four‑zone
  country. A zone is offered only when it covers at least 0.5% of the country's
  populated places.

The database keys countries by an integer `country_id`; `CountryIsoMap.idToIso`
and `CountryIsoMap.isoToId` are public for callers that persist or branch on
ISO codes. The `calculationMethod` extension property on `CountryInfo` /
`CityEntry` (import
`io.github.bilalelsayed97.islamickit.infrastructure.config.calculationMethod`)
translates the database's own `calc_method` numbering through
`BundledMethodMap` — those ids are **not** aladhan ids, so never pass
`calculationMethodId` to `CalculationMethod.fromId`.

## aladhan-compatible JSON

Produce the exact response shape used by the aladhan Prayer Times API. The
serializers return an **insertion‑ordered** `Map<String, Any?>` tree, and
`JsonWriter.encode` — a dependency‑free encoder — turns it into the same text
as Dart's `jsonEncode`, character for character: key order included (`hijri`
before `gregorian`, the fixed nine‑key `offset` block), whole method angles
emitted as `18` rather than `18.0` (the serializer hands them over as `Int`),
other doubles in Dart's `double.toString()` form, `/` and Arabic text left
unescaped.

```kotlin
import io.github.bilalelsayed97.islamickit.application.serialization.toAladhanJson

val json: Map<String, Any?> = result.toAladhanJson()

val text: String = JsonWriter.encode(json)                  // compact, Dart jsonEncode form
val pretty: String = JsonWriter.encode(json, indent = "  ") // JsonEncoder.withIndent form
// {
//   "code": 200, "status": "OK",
//   "data": {
//     "timings": { "Imsak": "03:47", "Fajr": "03:57", ... },
//     "date": { "readable": "24 Apr 2014", "timestamp": "1398294000",
//               "hijri": { ...ar names, holidays... }, "gregorian": { ... } },
//     "meta": { "latitude": 51.508515, "method": {...}, "school": "STANDARD", ... }
//   }
// }

AladhanSerializer.calendarAladhanJson(month)            // data: [ ...day objects ]  (with " (tz)" suffix)
AladhanSerializer.annualCalendarAladhanJson(year)       // data: { "1": [...], ..., "12": [...] }
AladhanSerializer.nextPrayerAladhanJson(result, Prayer.ASR) // single‑entry timings
AladhanSerializer.methodsAladhanJson()                  // the /methods response
AladhanSerializer.qiblaAladhanJson(service.qibla(coords))
```

Choose a format: `result.toAladhanJson(format = TimeFormat.ISO8601)`. The tree
is plain Kotlin collections (`Map`, `List`, `String`, `Int`, `Long`, `Double`,
`Boolean`, `null`), so you can hand it to `org.json`, Moshi, Gson or
kotlinx.serialization instead of `JsonWriter` when byte‑for‑byte parity with
Dart does not matter.

## Timezones & DST

The library intentionally ships **no timezone database** in the calculation
core. You pass `utcOffset` for the target date and **include DST yourself** (for
London that's `UtcOffset.ofHours(1)` in summer, `UtcOffset.ZERO` in winter). The
bundled geocoder stores each city's *standard‑time* offset, which the `*ByCity` /
`*ByAddress` helpers apply automatically unless you set `utcOffset` explicitly.

On Android and the JVM the platform already knows the rules, so the DST‑correct
offset for a date is one line — and `CityEntry.timeZoneId` gives you the IANA
name to feed it:

```kotlin
val date = CivilDate(2014, 4, 24)
val london = TimeZone.getTimeZone("Europe/London")
val offset = UtcOffset.of(london, date) // +01:00 (BST); the offset at local noon
val params = CalculationParameters(
    method = CalculationMethod.ISNA,
    utcOffset = offset,
    timezoneName = london.id,
)

// From a GPS fix, DST included:
val entry = directory.nearestCity(51.5074, -0.1278)!!     // CityEntry(London, GB), "Europe/London"
val zone = TimeZone.getTimeZone(entry.timeZoneId!!)
val auto = service.autoParamsForCityEntry(entry).copy(utcOffset = UtcOffset.of(zone, date))
```

`UtcOffset.of(timeZone, epochMillis)` takes an instant instead, `ZoneId.utcOffsetAt(date)`
is the `java.time` equivalent, and `PrayerTime.toEpochMillis()` gives you the
absolute instant to display in whatever zone you like.

## Thread-safety & lifecycle

- Every value type (`CivilDate`, `CalculationParameters`, `PrayerResult`, …) is
  an immutable `data class` or a final class with `val` fields; enums and the
  generated tables are read‑only. There is no global mutable state and no cache.
- `PrayerTimesService` holds only `val` collaborators. Construct one and share
  it across threads, coroutines and `WorkManager` workers freely. Calculations
  are pure CPU work — a day's timings are cheap, an annual calendar is 365 of
  them, so run calendars off the main thread.
- `BundledCityDatabase.materialize` / `open*` are blocking I/O and annotated
  `@WorkerThread`. The first call copies 37 MB; later calls only open the file.
- `SqliteCityGeocoder` and `SqliteCityDirectory` run each query on the **calling
  thread** against one read‑only `SQLiteDatabase`. Android's `SQLiteDatabase` is
  itself thread‑safe, so concurrent calls are safe but serialize on the single
  connection. Queries take milliseconds; keep them off the main thread anyway.
  Every `Cursor` is closed before a method returns. A failing query propagates
  its `SQLiteException`, as the Dart package propagates `sqlite3` errors.
- **Lifetime.** Open once per process and keep the `Handle` (or the geocoder /
  directory) in an `Application`‑scoped singleton. `close()` closes the
  underlying connection; a `Handle`'s geocoder and directory share one, so
  closing any of the three closes all of them. Do not open per screen or per
  call.
- **App widgets and workers** run in your app's process by default, so they can
  use the same singleton. If they only need times for a location you already
  resolved, persist the `Coordinates` and `CalculationParameters` fields and
  compute with `:core` alone — no database needed at that point.
- **R8 / ProGuard.** The library uses no reflection; `consumer-rules.pro` is
  empty on purpose.

## From Java

The API is annotated for Java callers: `@JvmOverloads` on the facade's methods
and the value‑object constructors, `@JvmStatic` factories, `@JvmField` constants
(`UtcOffset.ZERO`, `Tune.NONE`, `Prayer.DAILY_OBLIGATORY`). Extension functions
are reachable through their owners (`AladhanSerializer.toAladhanJson(result)`,
`JavaTimeInterop.toInstant(prayerTime)`).

```java
PrayerTimesService service = new PrayerTimesService();

// Telescoping constructor: arguments in declaration order, up to the last one you need.
CalculationParameters params = new CalculationParameters(
        CalculationMethod.ISNA, null, AsrSchool.STANDARD, null, null,
        HighLatitudeRule.MIDDLE_OF_NIGHT, UtcOffset.ofHours(1));

PrayerResult result = service.timings(
        new CivilDate(2014, 4, 24), new Coordinates(51.508515, -0.1254872), params);

result.formatted(Prayer.FAJR);                 // "03:57"
result.formatted(Prayer.ASR, TimeFormat.H12);  // "4:56 pm"
String json = JsonWriter.encode(AladhanSerializer.toAladhanJson(result));
```


- **Ports** (`Geocoder`, `CityDirectory`, `HijriConverter`, `TwilightStrategy`)
  are interfaces in the domain; concrete adapters live in infrastructure or the
  `:geocoding` module and are injected via the service constructor.
- **Strategy** for time formats, high‑latitude rules, and twilight; **Factory**
  for Hijri converters; **Facade** for the top‑level API; **Value Objects**
  throughout.
- Files marked *generated* (and the `CalculationMethod` table and enum strings)
  are emitted by the Dart package's `tool/generate_native_data.dart`, so every
  table and Unicode literal is byte‑identical to Dart.
- The engine never rounds through the host: CI rejects `Math.round`,
  `roundToInt` and `roundToLong` in `core/src/main`; `DartMath.round`
  reproduces Dart's half‑away‑from‑zero rule.

## Testing

```sh
./gradlew build                          # everything: compile, all tests, lint, both artifacts
./gradlew :core:test                     # 26,772 JUnit 5 tests, a few seconds, no Android SDK needed
./gradlew :core:test --tests '*Conformance*'   # only the cross-language fixtures
./gradlew :geocoding:testDebugUnitTest   # 36 Robolectric tests against the real 37 MB database
./gradlew publishToMavenLocal            # what JitPack runs: core-0.3.1.jar + geocoding-0.3.1.aar
```

The build needs JDK 17 and, for `:geocoding`, Android SDK platform 36. The
Robolectric tests emulate **SDK 35** (`robolectric.properties`): that is the
newest level Robolectric 4.17 runs on JDK 17 — emulating SDK 36 requires
Java 21 — while the module still compiles against SDK 36. The query tests
open the committed 37 MB asset in place, so they exercise the real database.

Three layers of tests:

1. **Ported Dart tests, 1:1** — the solar core against Meeus' worked examples
   25.a and 7.a; prayer times against the published Adhan reference vector
   (Raleigh NC, 2015‑07‑12, ISNA, Hanafi: `4:42 am`, `6:08 am`, `1:21 pm`,
   `6:22 pm`, `8:32 pm`, `9:57 pm`); ISNA London 2014‑04‑24 at +01:00 (Fajr
   `03:57`, Sunrise `05:46`, Dhuhr `13:00`, Asr `16:56`, Maghrib `20:12`, Isha
   `22:02`, Midnight `00:05`); Stockholm at the solstice bounded to `00:50`;
   Moonsighting London (`04:04` / `21:21`); the Ramadan Isha switch; the method
   table as an explicit list; all four Hijri methods (UAQ 2025‑02‑14 →
   1446‑08‑15, 29 days; sighting overrides; range errors); the qibla reference

   (Tehran `+03:30`, Delhi `+05:30`); and the directory (`nearestCity(30.06263,
   31.24967)` → Cairo, `Africa/Cairo`; 251 countries).
2. **Kotlin‑only tests** — `CivilDate` normalisation and weekdays, the
   `java.time` bridges, the ordered `JsonWriter`, Dart‑compatible double

## Parity notes

Every deviation from the Dart package is deliberate and listed here. Anything
not on this list is meant to match exactly — a mismatch is a bug.

| Dart | Kotlin | Why |
|---|---|---|
| `ArgumentError` / `StateError` | Unchecked `IllegalArgumentException` (`require`) / `IllegalStateException` (`check`, `error`), carrying the Dart message text | The Kotlin idiom; Kotlin has no checked exceptions, so nothing forces a `try`. The Ramadan lookup catches only `IllegalArgumentException`, as Dart catches only `ArgumentError`. |
| `copyWith(...)` on `const` value objects | `data class` + `copy(...)` | Same immutability. `copy()` is a **superset**: it can set a nullable field back to `null` (`copy(timezoneName = null)`), which `copyWith` cannot. `MethodParams.forRamadan()` is kept. |
| `DateTime` (date‑only / with time) | `CivilDate`, `CivilDateTime` | The engine is timezone‑free; these types make that explicit and keep the API on `minSdk 24` without desugaring. `CivilDate(y, m, d)` is **strict**; `CivilDate.normalized(y, m, d)` reproduces Dart's overflow (day 0, month 13, …) where the facade needs it. `java.time` bridges are additive. |
| `Duration utcOffset` | `UtcOffset`, which **stores whole seconds** (`totalSeconds`; `totalMinutes` and `hours` truncate toward zero) | The Dart engine reads the `Duration` in seconds; keeping seconds preserves historical sub‑minute zone offsets from `TimeZone` exactly. |
| `PrayerTime.toUtc()` → `DateTime` | `PrayerTime.toEpochMillis(): Long?` (+ `toInstant()` / `toZonedDateTime()` on API 26+) | No platform date type in the core API; the millisecond value equals Dart's `toUtc().millisecondsSinceEpoch`. |
| ISO‑8601 formatting adds minutes to a local `DateTime` | Civil‑date arithmetic only (no host time zone) | Avoids a latent host‑DST leak in the Dart path; the fixtures are generated under `TZ=UTC`, where both agree. |
| `List.sort` (unstable) in the geocoders | Stable ordering with a deterministic tiebreak: curated — dataset order after `score`; SQLite — `(score, rank, row index)` | Dart leaves tie order unspecified; fixtures pin only unique winners. |
| `double.toString()` for `TimeFormat.float`, `Coordinates.toString()` and JSON doubles | `DartMath.doubleToString` — shortest round‑trip digits laid out by Dart's rules (`13.0`, `3.95`, `1e+21`, `1e-7`) | `Double.toString()` on the JVM differs in digit selection on older runtimes and in exponent thresholds/format (`1.0E21`); the port reproduces Dart's so the strings match byte for byte. |
| `x.round()` | `DartMath.round` (half away from zero) | `Math.round` / `roundToInt` round half **up**, which differs for negative halves; CI forbids them in the engine. |
| `CityDirectory` is a concrete SQLite‑backed class (loaded via `loadBundledCityDirectory()` in the Flutter entrypoint) | `CityDirectory` is an **interface** in `:core`; `SqliteCityDirectory` implements it in `:geocoding` | The core must stay free of Android and SQLite, yet the facade needs the port for `autoParamsForCoordinates`. It also makes the directory fakeable in unit tests. |
| `loadBundledCityGeocoder()` / `loadBundledCityDirectory()` (async, `rootBundle`) and `SqliteCityGeocoder.openFile(path)` | `BundledCityDatabase.open(context)` / `openGeocoder` / `openDirectory` (blocking, `@WorkerThread`) and `SqliteCityGeocoder(BundledCityDatabase.openDatabase(file))` | Android assets have no file path, so the database is materialized to `noBackupFilesDir` once; blocking calls leave the threading model (executor, coroutines, WorkManager) to the app. |
| Enum values `firstThird`, `h12NoSuffix`, `iso8601`, `middleOfNight`, … | `UPPER_SNAKE` entries: `FIRST_THIRD`, `H12_NO_SUFFIX`, `MIDDLE_OF_NIGHT` — and **`ISO8601`** (no underscore, like `H24` / `H12`) | Kotlin naming convention. Entry names never reach any output: `key` / `code` / `metaValue` carry the Dart strings. |
| Extension `XL10n` with `title` / `description` per enum | The `Localized` interface, implemented by every enum | One type to program a settings UI against; the strings are generated from Dart. |
| Top‑level `calendarAladhanJson(...)`, `methodsAladhanJson()`, … ; constants `invalidTime`, `kCountryIdToIso`, `kIsoToCountryId` | Members of `AladhanSerializer` (plus `PrayerResult.toAladhanJson()` / `toAladhanData()` extensions); `TimeFormatting.INVALID_TIME`, `CountryIsoMap.idToIso` / `isoToId`, `Tune.NONE`, `MethodAdjustments.NONE`, `Prayer.DAILY_OBLIGATORY` | Namespacing for Kotlin and Java callers. |
| `Map<String, dynamic>` + `jsonEncode` | Insertion‑ordered `Map<String, Any?>` + `JsonWriter.encode` | No JSON dependency in the core, and guaranteed key order and number formatting identical to Dart. |
| `int` timestamps | `DateInfo.timestamp` and epoch values are `Long`; Julian day numbers and seconds‑of‑day are `Int` | Dart `int` is 64‑bit; JVM `Int` is not. |
| SQLite parameters bound by Dart type | `TypedQuery` binds `Int` → INTEGER, `Double` → REAL, `String` → TEXT | Android's `rawQuery(String[])` binds everything as TEXT, which changes `LIMIT ?`, `BETWEEN ?` and the distance arithmetic. |

Two behaviours that look like deviations but are **not** — they match the Dart
source exactly and are pinned by fixtures:

- `LocationDefaults` maps **VN → Makkah**. The Dart README's country list omits
  it; the Dart source has it, and so does this port.
- The **mathematical** Hijri calendar reports `monthLength` **30 for every
  month** (it does not track true month lengths), while the table methods
  report 29 or 30.
